## 1. 何が起きたか

日次PDCAトラッキングの **9/12・9/13・9/14 の3列が、丸ごと行ズレした状態で上書き**されていた。

| 現レイアウトの行 | 入っていた値 | 本来その値がある行 |
|---|---|---|
| 11 ウェビナーLP PV累計 | 2449 | 50 セミナーLP PV累計 |
| 23 ウェビナーLP登録数 | 139 | 62 セミナーLP登録数 |
| 32 ウェビナー予約数 | 50 | 71 セミナー予約数 |
| 41 視聴完了率 | 240000（`24000000%`と表示） | 48 売上金額 |

**行64〜73だけが無傷**だった。これが被害の指紋になった。

## 2. 原因

2026-09-11の並べ替え（`9691c97`）より**古い行番号を持つコード**が書いていた。
古い版は書き込み範囲が `11〜63` 固定で、行64〜73を知らない。だから64〜73が残る。

該当する挙動を持つのは `backup/sync_daily_monolithic.py`、および
9/11 23:11より前に `deploy.sh` で配られた本番コピー。
**どちらが動いたのかは特定できていない**（Googleがスプレッドシートの更新履歴を
間引くため、壊した実行そのものを追えなかった）。

## 3. なぜ4日間気づかなかったか

**既存の安全確認は行ズレを1つも検知しない。**

- 「列見出し（9行目の日付）の一致」→ 列は合っているので通る
- 「累計が前日より減っていないか」→ 前日列も同じようにズレていれば通る

9/14朝に初めて止まったのは、逆行チェックが**偶然**14/24項目で引っかかったからで、
設計として検知したわけではない。並べ替えコミットのメッセージ自身が
「★行がズレても既存の安全確認は何も引っかからない」と警告していた。

## 4. 直したこと（2026-09-15）

### ① 行ズレを検知する関門を追加

`config.ROW_GROUP_LABELS` に「行番号 → B列の見出しに含まれるべき文字列」を置き、
`sheets_client.verify_row_alignment()` が**書き込み前に**突き合わせる。
不一致なら書かずに `RuntimeError` で止まる。

壊すより止まる方が損害が小さい。ラベル由来の視聴状況は埋め直せないため。

### ② 値を持たない行を空欄で潰すバグを修正

`sheets_client.write_date()` は対象列の行11〜73を一括で置き換える。
このリポジトリは**行32〜41（ウェビナー予約数・視聴状況）を1つも計算していない**ので、
そこに空文字が入り、岡安側が書いた値を毎朝消していた。

元のコードは残すつもりの `if` が空文字を代入していて機能していなかった:

```python
val = cell_updates.get(r, "")
if val == "" and r in prev_vals:
    val = ""            # ←何もしていない
```

修正後は、書き込み前に対象列の現在値を読み、値を持たない行はそれを書き戻す
（`read_column(..., raw=True)`。整形済み文字列を書き戻すと `"50%"` が文字列として
入ってしまうため、生の値で読む）。

### ③ `backup/sync_daily_monolithic.py` を実行できないようにした

冒頭に理由を書き、`__main__` で `SystemExit` する。読むのは自由。

## 6. 教訓

**行番号を持つコードが2つ以上のMacで動くなら、行番号と見出しの突き合わせを必ず入れる。**
列の検証だけでは足りない。そして「片方のMacにしか無い集計」は、
もう片方の一括書き込みに毎朝消される前提で設計する。
